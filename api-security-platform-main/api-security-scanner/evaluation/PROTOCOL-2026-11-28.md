# Experimental protocol — retraining comparison

**Date: 2026-11-28. Frozen BEFORE any result is seen.**
**Status: governing the retraining experiment (Claude's plan, as
strengthened by the supervisor 2026-11-28). Any change requires a new
dated version of this file stating what changed and why. K, the
metrics and the success rule must never be chosen after seeing the
numbers.**

## Amendment 2026-11-28 (supervisor's stop rule)

What changed, and why:

- **Expected groups 10 → ~5–6 apps.** The original plan listed ten
  DynaST apps; the supervisor set the collection limit now, before
  the numbers arrive: fastapi, php and nestjs, plus one or two more
  REST-style apps (laravel, rails, springboot candidates, each
  checked with its own mapping first). §2 is updated accordingly.
- **Minimum data ~8 groups / ~100 positives → ~60 unique (route,
  parameter, category) positives, with at least 5 in each of the
  main categories.** The conclusion threshold is now counted in
  unique bugs, not rows — rows from one app are correlated. Below
  it, `retrain.py` runs only as a clearly labeled pipeline check.
- **Threshold rule added (§5): any threshold is chosen inside the
  training folds only.** The original protocol did not state this;
  the supervisor named the two evaluations separately (scanner vs
  model) and the fold-only threshold choice is part of the model
  evaluation. The current scripts use fixed FPR levels, so no tuned
  threshold exists yet.
- **Expectations set (§3):** with ~5–6 apps of data, the tabular
  models are the realistic candidates; the LSTM and autoencoder
  probably will not clear the bar, and dropping them with the
  evidence is a valid outcome.

## 1. Dataset

- Labeled files from `evaluation/label_dataset.py` only — labels come
  from the ground-truth join (endpoint, parameter, category), never
  from the scanner's own findings.
- Canonical sessions only. A re-scan supersedes its earlier session
  (e.g. php vuln session 5 is superseded by session 6) — the dedupe
  guard in `retrain.py` keeps the latest per (group, mode) and warns.
- `needs_auth` items are excluded from labels entirely (labeler) and
  from TP/FP (scorer). Incidental findings (real unlisted bugs found
  on a safe twin, e.g. the 3 fastapi XSS reflections) are recorded as
  dated incidental GT items, excluded from both TP and FP, labeled 1
  for training.
- `probe_effective` is reported alongside every result; a probe whose
  response never showed the bug is not a fair positive.

## 2. Groups and folds

- One group per app: the vulnerable app and its patched twin are ONE
  group (training on one twin and testing on the other is leakage).
- Expected groups (~5–6, amended 2026-11-28 — see the amendment at
  the top): fastapi, php, nestjs, plus one or two more REST-style
  apps (laravel, rails, springboot candidates, each checked with its
  own mapping first).
- Folds: leave-one-group-out. Every fold's train/test n and positives
  are printed.
- **Minimum data to draw conclusions: ~60 unique (route, parameter,
  category) positives, with at least 5 in each of the main
  categories.** Below that, `retrain.py` may run only as a clearly
  labeled pipeline check (dry run) — no conclusions, no model kept
  or removed on the basis of the numbers.

## 3. Models

- Tabular (15 features, schema response-diff-14-v1): Logistic
  Regression, Random Forest (300 trees), Gradient Boosting
  (HistGradientBoosting).
- **Differential-only ablation arm (planned, not optional):** the same
  three models trained on the 8 features that do not mirror Layer 1
  evidence (status_changed, size_delta_ratio, time_delta_ratio,
  body_diff_ratio, content_type_changed, status_class,
  response_size_log, response_time_s). If an ablation model beats the
  rules, that is independent signal. If it does not, say so.
- Text: TF-IDF (max 2000 features, 1–2 grams, sublinear) + Logistic
  Regression, trained per fold, vs the shipped LSTM's logged
  probability on the same folds. The LSTM itself is NOT retrained.
- `scanner_label` is excluded from every ML-alone model.

## 4. Baselines (fixed, untrained scores on the same pairs)

- Rule baseline: error_keyword_delta > 0 OR payload reflected.
- Shipped ML anomaly score, shipped LSTM probability, shipped
  autoencoder error.
- Signature points, scanner verdict (Confirmed = 1).

## 5. Metrics

- **PRIMARY — within the Suspected group** (the pairs the scanner
  already called Suspected; the layer where the noise lives):
  - PR-AUC with bootstrap 95% CI.
  - **Per-scan Precision@10 and Recall@10, K=10**: each scan ranked
    separately, averaged across scans. A reviewer looks at the top 10
    findings of one scan, not a pooled list. A scan with fewer than 10
    Suspected pairs uses min(10, n) as the precision denominator;
    recall averages only over scans with >= 1 Suspected positive.
  - Pooled P@10 / R@10 within Suspected are reported in the same
    table as SECONDARY.
- Secondary — pooled out-of-fold, all positives and effective-only
  positives: PR-AUC with CI, recall at FPR 0.01 / 0.05 / 0.10, pooled
  P@10 / R@10.
- **Accuracy is not a metric** (the negative class dominates).
- TF-IDF top features are inspected per fold for app-boilerplate
  leakage.
- **Thresholds (amended 2026-11-28): any threshold is chosen inside
  the training folds only** — never on the fold being tested, never
  on pooled results. The current scripts use fixed FPR levels
  (0.01 / 0.05 / 0.10) rather than tuned thresholds; the rule binds
  any future threshold tuning.

## 6. Success rule

A candidate model is adopted only if ALL of these hold:

1. Within-Suspected PR-AUC point estimate exceeds the rule baseline's
   PR-AUC, AND its per-scan mean P@10 exceeds the baseline's per-scan
   mean P@10.
2. The result holds on effective-only positives as well (secondary
   block).
3. For a claim of *independent* signal (beyond re-weighting Layer 1),
   the differential-only ablation arm must also beat the rule
   baseline on (1).
4. All numbers are reported with their bootstrap 95% CIs and the
   group/positive counts per fold. Nothing is quoted without its
   interval.

## 7. Autoencoder decision

- Remove if PR-AUC ≤ max(chance × 2, 0.05) on the full dataset, and
  say why. Keep (and re-measure) if above chance. Removal is a
  separate code change after the numbers.

## 8. Held-out rule (unchanged)

- Juice Shop and crAPI stay held out, each scored ONCE at the end on
  the final frozen system. A poor result is reported as is; any later
  fix becomes v2, tested on a different untouched app.

## 9. What this protocol does not cover

- Detection reliability (does the scanner prove what it claims?) and
  discovery reliability (does it find the endpoints?) are tracked
  independently — a model cannot fix an undiscovered endpoint or weak
  evidence. Discovery is measured as two-part recall (found the
  endpoint vs detected given the endpoint) from SURFACE.yaml.
